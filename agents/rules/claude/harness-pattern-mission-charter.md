# 공통 하네스 패턴: 미션 헌장 분리 (Mission Charter Separation)

> 이 파일은 `~/.agents/rules/claude/CLAUDE.md` 하네스 인덱스에서 참조됨. 하네스를 신규 구축하거나 기존 하네스에 "기본 프롬프트/스탠스 관리"를 도입할 때 로드한다. 레퍼런스 구현: **codebase-analyst**.

## 무엇인가

여러 에이전트가 **공유하는 분석/작성 스탠스**(왜·무엇을·얼마나 깊이)를 하나의 정전 파일(`references/mission-prompt.md`)로 분리하고, 오케스트레이터가 이를 로드해 모든 에이전트 호출에 주입하는 패턴.

목적은 두 가지를 한 파일로 충족하는 것:
1. **주입** — 단일 source of truth. 스탠스를 바꾸려면 이 파일만 고치면 전 에이전트에 일관 반영.
2. **아카이브** — 하네스가 어떤 의도로 만들어졌는지 보여주는 원문 헌장. 언제든 참고.

## 왜 분리하는가

- 스탠스가 6개 에이전트 정의에 흩어져 있으면, 태도를 바꿀 때 6곳을 고쳐야 하고 drift가 생긴다.
- 원본 프롬프트를 **통째로** 에이전트에 주입하면, 프롬프트의 "실행 구조 서술"(예: "5개 에이전트가 각각 수행 → 종합 보고서")이 하네스 워크플로우와 **중복**된다. 렌즈를 늘리거나 보고서 구조를 바꾸면 프롬프트와 하네스가 어긋난다.
- 그래서 프롬프트를 두 층으로 가른다:
  - **스탠스(왜·무엇을·얼마나 깊이)** → 주입 (single source of truth)
  - **실행 구조(누가·언제·어떻게)** → 하네스가 소유 (SKILL.md / 에이전트 / 템플릿). 주입하지 않고 아카이브로만 보존.

## 구조 (codebase-analyst 기준)

```
skills/{harness}/references/mission-prompt.md
├── 미션 변형 선택 표        ← (선택) deep/quick 등 변형이 여러 개일 때
├── 변형별 INJECT 블록       ← ---INJECT-START:{id}--- ~ ---INJECT-END:{id}---
│                              오케스트레이터가 $MISSION으로 로드 → 전 에이전트 주입
├── 원문 아카이브            ← 원본 프롬프트 전문 (주입 안 함, 기록용)
└── 원문 → 하네스 매핑 표    ← 실행 구조 서술이 하네스 어디서 구현되는지
```

**오케스트레이터 배선:**
- Phase 0: (변형이 여럿이면) 사용자 키워드로 변형 `$VARIANT` 선택
- Phase 1: 해당 INJECT 블록을 `$MISSION`으로 로드
- 에이전트 호출: 모든 프롬프트 **맨 앞에 `$MISSION` 포함**

**INJECT 블록 작성 원칙:**
- 스탠스(태도·목표·관점·깊이)만 담는다. 렌즈 개수·산출물 파일명·워크플로우 단계는 넣지 않는다.
- "너는 이 헌장을 너의 역할 관점에서 수행한다" 같은 역할 위임 문장으로 끝맺어, 단일 헌장이 여러 에이전트에 공유됨을 명확히 한다.

## 변형(variant) — 선택

같은 하네스를 다른 깊이/목적으로 쓰고 싶을 때 INJECT 블록을 여러 개 둔다 (예: deep/quick). 변형은 **스탠스 차이만** 담고 실행 골격(에이전트 구성·산출물 구조)은 공유한다. 변형마다 다른 골격이 필요하면 그건 새 하네스 신호다.

## 적용 대상 판단

| 하네스 성격 | 패턴 적합성 |
|------------|-----------|
| 고정 다중 에이전트가 **공유 스탠스**로 분석/작성 (codebase-analyst, content-expert) | ✅ 적합 — 정전 분리 효과 큼 |
| 단일 에이전트 / 대화형 컨설팅 (aws-expert 상담 모드) | △ 스탠스가 입력마다 달라지면 효과 작음 — 도입 신중 |
| 산출물이 매번 동적 생성되고 공유 스탠스가 약한 경우 | ✗ 불필요 — 오버엔지니어링 |

> 모든 하네스에 기계적으로 적용하지 않는다. "여러 에이전트가 공유하는 안정적 스탠스가 있는가?"가 도입 기준이다.
