# 재설명 요청 시 인과 구조화 설명

사용자가 이전 설명을 다시 풀어달라고 요청할 때 적용하는 설명 형식.

## 트리거

- "다시 설명해줘", "이 말을 다시 설명해줘"
- "무슨 말이야?", "이해가 안 돼", "좀 더 쉽게"
- 이전에 한 설명·보고·경고 문장을 인용하며 풀이를 요청할 때

## 형식 — 인과 사슬을 섹션으로 분리

설명을 한 덩어리로 쓰지 않고, 인과관계 단계마다 소제목(`##`)을 붙여 분리한다.

| 순서 | 섹션 (예시 제목) | 답해야 할 질문 |
|---|---|---|
| 1 | "어떤 기능 이야기인가" | 지금 무엇에 대해 말하는가? 대상을 사용자 눈에 보이는 것(화면·동작·개념) 기준으로 식별 |
| 2 | "무엇이 문제였나 / 어떻게 동작했나" | 원인 또는 기존 상태. 왜 그런 일이 일어났는지 매커니즘까지 |
| 3 | "이번 수정으로 무엇이 달라졌나 / 그래서 어떻게 되나" | 결과·영향. 전/후 비교를 명시 (수정 전: → 수정 후:) |
| 4 | (해당 시) 확인 방법 | 사용자가 직접 검증할 수 있는 구체적 시나리오 1개 |

섹션 제목은 위 예시를 그대로 쓰지 않아도 된다 — 주제에 맞게 바꾸되 "대상 식별 → 원인/기존 상태 → 변화/결과 → 검증" 순서의 인과 흐름은 유지한다.

## 작성 원칙

- **용어 먼저**: 코드 식별자(`sendTimeType` 등)가 등장하면 그것이 화면/도메인에서 무엇인지 먼저 한 문장으로 정의한 뒤 사용한다.
- **사용자 관점 우선**: 코드 구조가 아니라 화면 동작·업무 흐름 기준으로 서술하고, 코드는 근거로만 붙인다.
- **전/후 비교는 대구로**: "수정 전: …" / "수정 후: …" 처럼 같은 문형으로 나란히 보여준다.
- **마무리는 행동**: 검증 시나리오나 "의도와 다르면 알려달라"는 되돌림 옵션으로 끝낸다.

## 레퍼런스 사례

cdp-frontend MCCWC-10011 작업(2026-06-12)에서 "sendTimeType 자동 설정 복원" 경고 문장을 재설명한 응답 — "어떤 기능 이야기인가 → 무엇이 망가져 있었나 → 이번 수정으로 무엇이 달라졌나 → 확인 시나리오" 구조. 사용자가 이 형식을 명시적으로 채택함.
