# 응집도 (Cohesion) — 핵심 원칙

> **정의:** 응집도란, 수정되어야 할 코드가 항상 같이 수정되는지를 말한다. 응집도가 높은 코드는 한 부분을 수정해도 다른 부분에서 의도치 않은 오류가 발생하지 않는다. 함께 수정되어야 할 부분이 **구조적으로** 함께 묶여 있기 때문이다.
>
> 한 문장 휴리스틱: **"함께 변하는 코드가 함께 모여있는가?"**

---

## 1. 함께 수정되는 파일을 같은 디렉토리에 두기

**안티패턴:** `components/`, `containers/`, `hooks/`, `utils/`처럼 **모듈 종류(역할)별**로 디렉토리를 나눈다. 같은 도메인 기능에 속한 파일들이 트리 곳곳에 흩어져, 한 기능을 수정할 때 4~5군데를 동시에 손봐야 한다.

**원칙:** **도메인 단위(`src/domains/Domain1/{components,hooks,utils}`)** 로 묶는다. 함께 수정되는 파일이 물리적으로 인접하면 의존 관계가 한눈에 보이고, 기능 삭제 시 미아 코드(orphan)가 남지 않는다.

**리뷰 시그널:**
- import 경로에 `../../../OtherDomain/...` 같은 **다른 도메인을 깊이 거슬러 올라가는 상대경로**
- 한 PR diff가 `hooks/`, `components/`, `utils/` 세 군데를 동시에 건드림
- 컴포넌트 삭제 후 그 컴포넌트만 쓰던 hook/util이 트리 어딘가에 살아남음

```
// 안티패턴
src/{components,containers,hooks,utils}

// 개선
src/domains/Order/{components,hooks,utils}
src/domains/Cart/{components,hooks,utils}
```

## 2. 매직 넘버 없애기 (응집도 관점)

**안티패턴:** `await delay(300)`, `if (status === 404)`, `setTimeout(fn, 86400)` — **의미 없는 숫자**를 사용처에 직접 박는다. 같은 의미의 숫자가 여러 파일에 중복되어 있으면 한쪽만 수정 시 silent break.

**원칙:** 숫자에 **이름 있는 상수**(`ANIMATION_DELAY_MS`, `SECONDS_PER_DAY`)를 부여하고, 의미적으로 묶이는 코드(예: 애니메이션 정의와 그 애니메이션을 기다리는 delay)를 한 군데서 참조하게 만든다.

**리뷰 시그널:**
- `delay(300)`의 `300`과 CSS `transition: 0.3s`가 **다른 파일에 따로** 존재 → 애니메이션을 0.5s로 바꿨을 때 delay는 그대로 → silent break
- 같은 숫자(`86400`, `404`)가 여러 파일에 중복
- 숫자 옆에 의미를 설명하는 주석 → 그 주석이 곧 상수 이름이어야 함

```ts
// Before
await postLike(url); await delay(300); await refetchPostLike();

// After
const ANIMATION_DELAY_MS = 300;
await postLike(url); await delay(ANIMATION_DELAY_MS); await refetchPostLike();
```

> 주의: 가독성의 §5 매직넘버와 겹치는 면이 있으나, 응집도 관점은 **"숫자와 그 의미가 같은 곳에 있는가, 흩어져 있어 함께 변하지 않는가"**에 초점을 둔다.

## 3. 폼의 응집도 생각하기

**안티패턴:** 폼의 응집 단위를 **무의식적으로** 선택. 필드 검증과 폼 전체 검증을 섞어 쓰거나, 필드 간 의존(예: 비밀번호 확인)이 있는데 필드 단위로 흩뿌려 둠.

**원칙:** 응집 단위를 **의도적으로** 고른다.
- **필드 단위:** 필드가 독립적이고 재사용성이 중요할 때. 결합도↓, 재사용성↑.
- **폼 전체 단위(zod 스키마 등):** 필드 간 의존이 있거나 일관성·흐름 파악이 중요할 때. 일관성↑, 재사용성↓.

**리뷰 시그널:**
- 같은 필드의 검증 규칙(예: 이메일 정규식)이 **컴포넌트와 서버 액션 양쪽에 중복**
- "비밀번호"와 "비밀번호 확인" 검증이 **각자의 필드 안에서** 서로를 참조 → 폼 스키마로 끌어올려야 함
- 필드 하나를 떼어 다른 폼에 재사용해야 하는데, 그 필드가 부모 폼의 다른 필드 상태를 직접 읽음 → 응집 단위가 잘못 잡힘

```ts
// 필드 단위 — 독립 재사용
<Input rules={{ required, minLength: 8 }} />

// 폼 전체 단위 — zod 스키마로 중앙화
const schema = z.object({ pw: z.string().min(8), pwConfirm: z.string() })
  .refine(d => d.pw === d.pwConfirm, { path: ["pwConfirm"] });
```

## 리뷰어 체크리스트

| # | 시그널 |
|---|---|
| 1 | 도메인이 다른 디렉토리로 흩어져 한 PR이 3+ 폴더 수정 / 미아 파일 잔존 |
| 2 | 같은 의미 숫자가 여러 파일에 중복 / 숫자와 그 의미가 떨어져 있음 |
| 3 | 같은 검증 규칙 중복 / 필드 간 의존을 필드 단위에서 처리 |
