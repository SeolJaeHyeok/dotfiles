# 기술 문서 작성 표준

## 문체 원칙

### 기본 톤
- **명확**: 모호한 표현을 피한다. "몇 가지" → "3가지", "빠르게" → "2초 이내"
- **간결**: 한 문장에 하나의 정보. 접속사로 3개 이상 연결하지 않는다
- **실용적**: 읽은 후 바로 행동할 수 있어야 한다
- **친절하되 장황하지 않게**: 존댓말 사용, 불필요한 인사/감사 제거

### 독자별 톤 조절
| 독자 | 전문 용어 | 코드 예제 | 배경 설명 |
|------|----------|----------|----------|
| 시니어 개발자 | 그대로 사용 | 핵심만 | 최소 |
| 주니어 개발자 | 첫 등장 시 설명 | 전체 실행 가능 | 중간 |
| 비개발자 | 가능하면 대체어 사용 | 스크린샷/결과만 | 충분히 |

## 구조 표준

### 헤딩 규칙
- H1: 문서 제목 (문서당 1개)
- H2: 주요 섹션
- H3: 하위 항목
- H4 이하: 가능하면 사용하지 않는다 (구조가 깊으면 문서를 분리)

### 코드 블록
- 언어 태그 필수: ````typescript`, ````bash`, ````json`
- 주석으로 핵심 포인트 표시
- 실행 가능한 완전한 예제 우선 (스니펫보다)
- 명령어에는 예상 출력도 포함

```bash
# 서버 시작
npm run dev
# 예상 출력: Server running on http://localhost:3000
```

### 테이블
- 3개 이상 항목 비교 시 테이블 사용
- 칼럼은 5개 이하로 유지
- 모든 셀에 값 채우기 (빈 셀은 "-" 또는 "N/A")

### 콜아웃
```markdown
> **Note**: 참고 사항

> **Warning**: 주의 사항 (데이터 손실, 보안 위험)

> **Tip**: 유용한 팁
```

## 문서 유형별 필수 섹션

### API 문서
1. 개요 (API의 목적)
2. 인증 방법
3. Base URL + 버전 정보
4. 엔드포인트별: Method, Path, Description, Parameters, Request Body, Response, Error Codes, Example
5. 에러 코드 레퍼런스
6. Rate Limit 정보

### 아키텍처 문서
1. 컨텍스트 (이 시스템이 해결하는 문제)
2. 아키텍처 개요 + 다이어그램
3. 주요 컴포넌트 설명
4. 데이터 흐름
5. 기술 선택 근거 (ADR)
6. 비기능 요구사항 (성능, 보안, 확장성)
7. 제약사항 및 트레이드오프

### 가이드/튜토리얼
1. 목표 (이 가이드를 끝내면 무엇을 할 수 있는가)
2. 전제 조건
3. 단계별 절차 (번호)
4. 검증 방법 (각 단계의 예상 결과)
5. 트러블슈팅 / FAQ
6. 다음 단계

### README
1. 프로젝트 이름 + 한 줄 설명
2. 배지 (빌드 상태, 버전, 라이선스)
3. 빠른 시작 (5줄 이내로 실행까지)
4. 설치 상세
5. 사용법 + 예제
6. 설정/환경 변수
7. 기여 방법 (또는 CONTRIBUTING.md 링크)
8. 라이선스

## 품질 체크리스트

작성 완료 후 확인:
- [ ] 모든 코드 예제가 실행 가능한가?
- [ ] 전문 용어가 첫 등장 시 설명되었는가?
- [ ] 외부 링크가 유효한가?
- [ ] 날짜/버전 정보가 최신인가?
- [ ] 목차가 있는가? (3 섹션 이상일 때)
- [ ] 독자가 다음 행동을 알 수 있는가?

## 한국어 기술 문서 규칙

- 영문 기술 용어는 한글 병기하지 않아도 됨 (API, SDK, endpoint 등)
- 다만 처음 등장하는 약어는 풀어 쓴다 (ADR(Architecture Decision Record))
- 코드 내 주석은 한국어, 코드 자체는 영어
- 외래어 표기: 공식 한국어 명칭이 있으면 사용 (예: 로드밸런서, 데이터베이스)
