# obsidian-archive

세션의 핵심 학습 / 결정 / 사고 사례 / 워크플로 패턴을 `~/Documents/Obsidian Vault/Inbox/` 로 정리 archive 한다. 미래의 자기가 6 개월 뒤 단독으로 열어 이해할 수 있는 *영구 자산* 을 만드는 게 목표.

## Purpose

작업 / 학습이 끝나면 그 안의 *재사용 가능한 패턴* 은 휘발성 세션 메모리에서 사라진다. Obsidian Vault 의 Inbox 는 *분류 애매한 초안 / 학습 노트* 의 자유 쓰기 구역이라 archive 의 첫 착지점으로 적합. 이 스킬은:

1. 세션 / 대화 내용에서 *재사용 가능한 핵심* 만 추려
2. vault 의 CLAUDE.md 컨벤션을 준수한 마크다운으로 잠그고
3. 미래 자기가 같은 주제로 돌아왔을 때 *그 노트 한 파일만 읽고* 본질을 회복할 수 있게 한다

## When to Use

호출:
- 사용자가 "Obsidian에 정리" / "Inbox에 archive" / "노트로 정리" / "방금 내용 노트로" / "정리해서 노트로 만들어줘" 라고 말할 때
- 세션 끝낼 때 회고로 학습 내용 보존하고 싶을 때
- 워크플로 / 사고 사례 / 라이브러리 패턴 / 결정 사슬 등 한 주제를 *미래 참조 가능* 한 형태로 잠그고 싶을 때

호출하지 않음:
- *프로젝트 코드베이스 안의 docs/* 에 들어가야 할 내용 — wellcheck 트랙이면 `/wc:compound`, 단발 결정이면 그 프로젝트 README/CHANGELOG
- 다음 세션 즉시 이어쓰기용 일시적 영속화 — `/wc:handoff` 또는 `/handoff`
- 사용자가 "그냥 알려만 줘" / "정리 안 해도 돼" 라고 한 경우

## Vault 컨벤션 (위치 + 규칙)

| 항목 | 값 / 규칙 |
|---|---|
| 저장 위치 | `~/Documents/Obsidian Vault/Inbox/` (`~/Docs` 아님 — `~/Documents`) |
| 파일명 | `<주제> (YYYY-MM-DD).md` — 한글/영문 혼용 OK, `/`·`\` 금지 |
| Frontmatter | 최소형: `created: YYYY-MM-DD` + `source: 회의 \| 개발 \| 학습 \| 외부 링크 \| 대화` |
| 최상위 `#` 제목 | **생략** — 파일명이 제목 역할 |
| 섹션 구분선 | `---` 사용 |
| Wikilink | 존재하는 노트만 `[[...]]` 로 — *깨진 링크 만들지 마* |
| Inbox 권한 | 자유 쓰기 (vault CLAUDE.md Phase 1 의 예외) |

> Vault 의 `~/Documents/Obsidian Vault/CLAUDE.md` 가 정식 계약. 이 스킬은 그중 *Inbox 작성* 부분만 일관 적용.

```markdown
## 개요

주제 한 단락 요약. 어떤 문제를 다루며 *어떤 사용자가* (보통 미래의 자기) *어떤 상황에서* 이 노트를 다시 찾을지.

## 핵심 개념

주제의 mental model. 표 / 다이어그램 / 의사코드 활용. 추상만 적지 말고 *왜 그렇게 되는지* 의 because 한 줄씩 포함.

## 예시 / 사례

실제로 본 흐름 — 명령 / 시나리오 / 코드 블록. *직접 밟은 사고가 있으면 반드시 포함*. 추상 설명만으로는 미래 자기도 헷갈림.

## 함정 / 주의

이 주제에서 *흔히 실수하는 패턴*. 같은 함정 재방문 방지가 노트의 가장 큰 가치 중 하나.

## 체크리스트 (optional)

같은 작업 다시 할 때 그대로 따를 수 있는 정석 흐름. 너무 추상이면 무가치 — *체크 가능한* 형태로.

## 참고

- 관련 있을 수 있는 노트 (vault 내 존재 확인 후 `[[...]]`)
- 외부 링크 / docs
- 이 노트가 어디서 왔는지 (세션 / PR / 이슈 번호)
```

각 절은 *실제로 쓸 내용이 없으면 생략 가능* — 빈 절을 채우려 작문 X.

## Multi-host 질문 추상화

파일명 / 덮어쓰기 / 위치 변경 등 사용자 동의 필요 시점에 **플랫폼이 제공하는 블로킹 질문 도구로 제시한다**:

- **Claude Code**: `AskUserQuestion` (옵션 + free-text)
- **Cursor / Codex**: 채팅·TUI 평문 + 번호 옵션 + 응답 대기

**어떤 플랫폼이든 사용자 응답 없이 파일을 작성·덮어쓰지 않는다.**

## Core Principles

1. **미래 자기 우선** — 6 개월 뒤 자기가 단독으로 읽고 이해할 수 있게. 세션 컨텍스트 의존 표현 ("아까 그", "방금 본") 금지.
2. **예시 필수** — 추상 설명만 적지 않는다. 실제 명령 / 시나리오 / 코드 / 사고 사례를 항상 동반.
3. **함정 명시** — 사고 사례가 있으면 *왜 그렇게 됐는지* + *어떻게 회피하는지* 둘 다.
4. **vault 컨벤션 준수** — 위치 (Inbox), 파일명 (날짜 접미사), frontmatter 최소형, 최상위 # 생략 — 모두 vault CLAUDE.md 가 정식 계약.
5. **사용자 동의 우선** — 파일명 / 덮어쓰기 / 위치 변경은 모두 *블로킹 질문* 후 진행. 자동 작성 X.
6. **깨진 wikilink 만들지 마** — `[[...]]` 는 *존재하는 노트* 만. 없으면 평문으로 안내.
7. **빈 절 채우지 마** — 6 절 골격은 가이드일 뿐. 실제 쓸 내용이 없는 절은 생략 (작문성 padding X).

## Phase 0: 주제 명확화

너무 추상적인 입력 ("이번 세션 정리해줘") 이면 *무엇을 archive 할지* 1 줄 받기 위한 블로킹 질문:

> "어떤 주제를 한 줄로 잠글까요? 예: 'stacked PR 워크플로', '오늘 트러블슈팅', 'React hook 패턴'."

이미 명확한 입력 ("방금 stacked PR 관련 이야기 정리해줘") 이면 바로 Phase 1.

## Phase 1: 파일명 / slug 결정

주제를 1-5 단어 *한글 또는 영문* 으로 압축 + 오늘 날짜 접미사:

- `<주제> (YYYY-MM-DD).md`
- 예: `Stacked PR 워크플로 — 함정과 정석 흐름 (2026-05-11).md`
- 예: `React useEffect 의존성 함정 (2026-05-11).md`

> 날짜: 사용자 머신의 *오늘* (시스템 시간). 미래 / 과거 날짜 임의 추정 X.

후보 파일명 한 번 *사용자 확인* (블로킹 질문). 동일 파일명 존재 시:
- "기존 파일이 있습니다. (1) 덮어쓰기 (2) 다른 슬러그 (3) 취소 — 어떻게 할까요?"

## Phase 2: 본문 작성

6 절 골격으로. 각 절은 *세션 컨텍스트* 에서 다음을 추출:

| 절 | 어디서 가져오나 |
|---|---|
| 개요 | 사용자의 원래 질문 / 문제 + 왜 정리하는지 |
| 핵심 개념 | 대화 중 *recurring 한 결정 / 모델* — "그래서 핵심은 X" 의 X 들 |
| 예시 / 사례 | 실제 실행한 명령 / 본 코드 / 밟은 사고 |
| 함정 / 주의 | 사용자 / 에이전트가 *틀린 길로 갔던 순간* + 왜 |
| 체크리스트 | 같은 작업 반복 시 *그대로 따를 수 있는* 단계 |
| 참고 | vault 내 관련 노트 (검색 후 존재 확인) / 외부 링크 / PR·이슈 번호 |

세션 컨텍스트가 부족하면 작문하지 말고 그 절 생략.

## Phase 3: vault 컨벤션 검증

작성 직전 self-check:
- [ ] 위치가 `~/Documents/Obsidian Vault/Inbox/` 인가
- [ ] 파일명에 `/`·`\` 가 없는가
- [ ] Frontmatter 가 `created: YYYY-MM-DD` + `source: ...` 형태인가
- [ ] 최상위 `#` 제목이 없는가 (파일명이 제목)
- [ ] `[[wikilink]]` 가 있다면 *존재하는 노트* 만 가리키는가
- [ ] 빈 절을 작문성으로 채우지 않았는가

## Phase 4: Write + 보고

`Write` 도구로 파일을 `~/Documents/Obsidian Vault/Inbox/` 에 작성. 완료 메시지에 절대 경로 명시:

> "✅ 작성 완료: `~/Documents/Obsidian Vault/Inbox/Stacked PR 워크플로 — 함정과 정석 흐름 (2026-05-11).md`"

> **Inbox 에서 다른 폴더로의 분류·이동은 사용자가 직접 한다.** 스킬은 Inbox 까지만 책임 — 작성 후 위치 추적 / 자동 이동 제안 X. 그게 vault 의 *Phase 1 제안형 쓰기* 정책과 Inbox 의 *자유 쓰기 구역* 역할의 경계.

옵션: vault 내 관련 노트 후보 1-3 개 (Grep 으로 검색) 제시 — *깨진 링크는 만들지 말고* 경로만 평문으로:

> "관련 있을 수 있는 노트:
> - `개발 기록/Git 관련/Rebase 정석.md` (존재 확인됨)
> - `MOC - 개발 기록.md`"

## Examples

### Good — 명확한 주제 + 사고 사례 포함

**입력**: "방금 stacked PR 관련 이야기들 정리해줘"

**Phase 1**: 파일명 후보 `Stacked PR 워크플로 — 함정과 정석 흐름 (2026-05-11).md`, 사용자 OK
**Phase 2**: 본문 작성
- 개요: stacked PR 패턴이 뭐고 왜 쓰는가
- 핵심 개념: 브랜치 체이닝 / 머지 순서 / auto-retarget 조건
- 예시: 3-PR 체인 만들기 + 머지 명령 + `git rebase --onto` 사용법
- 함정: API 로 raw ref 삭제하면 dependent PR close (실제 밟은 사고)
- 체크리스트: PR 만들 때 / 머지할 때 / 사고 시 복구 절차
- 참고: 이 노트의 출처 (PR #55·#56·#57)

**Phase 3**: vault 컨벤션 검증 통과
**Phase 4**: Write + 절대 경로 보고

왜 좋은가: 사고 사례 (API 직접 삭제 → PR close) 가 함정 절에 *왜 그렇게 됐는지* + *어떻게 회피* 까지 모두 포함. 미래 자기가 같은 함정 안 밟음.

### Good — 짧은 패턴 노트

**입력**: "오늘 본 `git rebase --onto` 사용법만 노트로"

**Phase 1**: 파일명 `git rebase --onto 사용법 (2026-05-11).md`
**Phase 2**:
- 개요: stacked rebase 의 정확한 replay 범위 지정
- 핵심 개념: `--onto <new> <old> <branch>` 의 의미
- 예시: 한 케이스
- (함정 / 체크리스트 / 참고는 생략 — 짧은 패턴 노트)

왜 좋은가: 6 절 골격을 *억지로 다 채우지 않음*. 짧은 주제는 짧게.

### Bad — 너무 추상

**입력**: "이번 세션 정리해줘"

**잘못된 대응**: 즉시 작성 시작 — 무엇을 정리할지 모름.

**올바른 대응**: Phase 0 의 블로킹 질문 → "어떤 주제를 한 줄로 잠글까요? 예: 'stacked PR', 'audit 스크립트 리팩터', ..." → 사용자 답변 후 진행.

### Bad — 깨진 wikilink

**잘못된 대응**: 본문에 `관련: [[React Hooks 정석]]` 박았는데 그 노트가 존재 안 함.

**올바른 대응**: Grep 으로 노트 존재 확인 → 없으면 *평문* 으로 안내 ("관련 주제: React Hooks (vault 에 노트 없음)").

### Bad — 빈 절 작문

**잘못된 대응**: 함정 절에 쓸 내용이 없는데도 골격이라고 "주의해야 한다 / 신중하게 해야 한다" 작문성 padding.

**올바른 대응**: 절 통째 생략. 6 절 골격은 *가이드*, 의무 X.

## Final Checklist

작성 직후 확인:
- [ ] 파일 경로가 `~/Documents/Obsidian Vault/Inbox/` 하위
- [ ] 파일명 끝에 ` (YYYY-MM-DD)` 접미사, `/`·`\` 없음
- [ ] Frontmatter 가 `created: YYYY-MM-DD` + `source: ...` 형태로 잠겨 있음
- [ ] 최상위 `#` 제목 없음 (파일명이 제목 역할)
- [ ] 적어도 *개요* + (*핵심 개념* OR *예시* OR *함정* 중 하나) 가 채워짐 — 빈 골격만 작성 X
- [ ] 사용된 `[[wikilink]]` 모두 vault 내 *존재* 확인됨
- [ ] 사용자 동의를 받은 파일명으로 작성됨 (자율 작성 X)
- [ ] 완료 보고에 절대 경로 명시됨

## Output

- 파일: `~/Documents/Obsidian Vault/Inbox/<주제> (YYYY-MM-DD).md`
- 콘솔: 작성 완료 + 절대 경로 + (옵션) 관련 노트 후보 1-3 개 평문 안내

## Related Skills

- `/wc:compound` (wellcheck-plugins) — *프로젝트 코드베이스* 안의 `docs/<slug>/SOLUTION.md` 로 *해결한 문제* 누적. 이 스킬은 *프로젝트 무관 학습* 을 Obsidian 으로.
- `/wc:handoff` (wellcheck-plugins) — *다음 세션 즉시 이어쓰기* 용 일시적 영속화. 이 스킬은 *영구 자산화*.
- `/checkpoint` (gstack) — *작업 중* 의 진행 상태 스냅샷. 이 스킬은 *작업 종료 후* 의 학습 추출.

## Why This Exists

세션이 끝나면 그 안의 *재사용 가능한 패턴* 은 휘발성 컨텍스트에서 사라진다. Vault 의 Inbox 는 *분류 애매한 초안* 의 자유 쓰기 구역으로 archive 의 첫 착지점에 적합. vault CLAUDE.md 가 정식 컨벤션이라 이 스킬은 그 규칙을 *항상 자동 준수* — 사용자가 매번 규칙 떠올릴 필요 없음.
