# 코드베이스 분석 미션 프롬프트 (정전 / Source of Truth)

> 이 파일은 두 가지 용도를 겸한다:
> 1. **주입** — 오케스트레이터가 Phase 0에서 변형을 선택하고 Phase 1에서 해당 변형의 "주입 블록"을 `$MISSION`으로 로드해 모든 렌즈 에이전트 + synthesizer 호출 프롬프트 맨 앞에 포함한다. 5개 렌즈가 동일한 분석 스탠스를 공유하게 만드는 'Team Big Five'의 공유 멘탈 모델의 일부.
> 2. **아카이브** — 이 하네스가 어떤 의도로 만들어졌는지 보여주는 원문 헌장. 언제든 열어 참고한다.
>
> **편집 규칙:** 분석 스탠스(태도·목표·관점)를 바꾸려면 **해당 변형의 주입 블록만** 고친다 → 전 에이전트의 분석 태도가 일관되게 바뀐다. 실행 구조(렌즈 개수·보고서 섹션·워크플로우)는 이 파일이 아니라 SKILL.md / 에이전트 정의 / report-template.md에서 관리한다.

---

## 미션 변형 선택 (오케스트레이터가 Phase 0에서 결정)

사용자 요청의 어조·키워드로 변형을 고른다. 단서가 없으면 **deep(기본)**.

| 변형 | 용도 | 트리거 키워드 | 실행 힌트 (오케스트레이터가 적용) |
|------|------|--------------|-------------------------------|
| **deep** (기본) | 심층 학습·참고. 인사이트 최대 추출 | 기본값, "깊게", "자세히", "학습용", "배울 점", "제대로 분석" | 5렌즈 풀 분석 + 8섹션 풀 보고서 |
| **quick** | 빠른 진단. 핵심 강점·리스크만 신속 식별 | "빠르게", "간단히", "핵심만", "진단", "훑어", "대충 봐줘" | 5렌즈 간결(각 상위 3~5개) + 1페이지 핵심 보고서(P0 위주) |

오케스트레이터는 선택한 변형 ID(`$VARIANT`)에 해당하는 INJECT 블록을 `$MISSION`으로 로드하고, 실행 힌트를 Phase 2(렌즈 출력 분량)·Phase 3(보고서 분량)에 반영한다.

## 변형: deep (기본 — 심층 학습/참고용)

> 마커: `---INJECT-START:deep---` ~ `---INJECT-END:deep---`

---INJECT-START:deep---

**[분석 헌장 — 심층]**

제공된 코드베이스를 시니어 소프트웨어 아키텍트, 스태프 엔지니어, 코드 리뷰어로 구성된 전문가 팀의 관점에서 분석하라. 단순히 코드를 설명하는 것이 아니라, 개발자가 실무에서 참고하고 학습할 수 있는 인사이트를 추출하는 것을 목표로 한다.

프로젝트의 아키텍처, 설계 패턴, 도메인 모델, 모듈 구조, 코딩 컨벤션, 테스트 전략, 인프라 구성, 성능 최적화 기법, 보안 고려사항, 그리고 주목할 만한 구현 기법을 식별하고 설명하라. 각 요소의 장점과 트레이드오프를 분석하고, 실제 코드 예시(`path:line`)를 근거로 설명하라.

무엇이 구현되었는지뿐 아니라 왜 그렇게 설계되었는지, 어떤 엔지니어링 원칙과 의사결정이 반영되었는지를 추론하고 설명하라. 또한 해당 프로젝트로부터 다른 개발자들이 자신의 프로젝트에 적용할 수 있는 실질적인 교훈과 베스트 프랙티스를 도출하라.

> 너는 이 헌장을 너의 렌즈 관점에서 수행한다. 위 식별 대상 전부를 혼자 다루려 하지 말고, 너의 렌즈에 해당하는 부분에 집중하되, 다른 렌즈가 더 깊이 볼 발견은 "교차 발견"으로 넘겨라.

---INJECT-END:deep---

## 변형: quick (빠른 진단용)

> 마커: `---INJECT-START:quick---` ~ `---INJECT-END:quick---`

---INJECT-START:quick---

**[분석 헌장 — 빠른 진단]**

제공된 코드베이스를 시니어 소프트웨어 아키텍트·스태프 엔지니어·코드 리뷰어 관점에서 **빠르게 진단**하라. 목표는 망라적 학습 자료가 아니라, 의사결정에 필요한 **가장 중요한 강점과 리스크**를 신속히 식별하는 것이다.

너의 렌즈에서 영향도가 큰 **상위 3~5개 발견에만** 집중하라. 모든 요소를 다루려 하지 말고, 시스템 전반에 영향을 주거나 즉시 주의가 필요한 것부터. 각 발견은 대표 코드 예시(`path:line`) 하나로 근거를 대고, 왜 중요한지와 트레이드오프를 한두 줄로 요약하라. 깊은 배경 설명·완전성보다 **즉시 판단 가능한 신호**를 우선한다.

> 너는 이 헌장을 너의 렌즈 관점에서 수행한다. 너의 렌즈에 해당하는 상위 신호에 집중하되, 다른 렌즈가 볼 발견은 "교차 발견"으로 넘겨라.

---INJECT-END:quick---

## 새 변형 추가하는 법

1. 위 형식으로 `## 변형: {id}` 섹션과 `---INJECT-START:{id}---` ~ `---INJECT-END:{id}---` 블록을 추가한다.
2. "미션 변형 선택" 표에 행 1개(용도·트리거 키워드·실행 힌트)를 추가한다.
3. SKILL.md는 변형 ID로 블록을 로드하므로 워크플로우 수정 불필요. 실행 힌트가 새로운 동작(예: 특정 렌즈만 실행)을 요구하면 그때만 SKILL.md를 손본다.

> 변형은 **스탠스(왜·무엇을·얼마나 깊이)** 차이만 담는다. 렌즈 구성·보고서 구조 같은 실행 골격은 변형 간 공유한다 — 변형마다 다른 골격이 필요하면 그건 새 하네스 신호다.

## 원문 아카이브 (¶1~4 전체 — 참고용, 주입하지 않음)

> 하네스 설계의 출발점이 된 원본 프롬프트 전문. ¶4(실행 구조)는 이미 하네스 워크플로우(SKILL.md Phase 2~3 + report-template.md)가 구현하고 있으므로 **주입하지 않는다** — 주입하면 하네스와 중복되어 렌즈/보고서 구조 변경 시 drift가 발생한다. 여기엔 "왜 이 하네스를 이렇게 만들었는가"의 기록으로만 보존한다. deep 변형의 주입 블록이 이 원문 ¶1~3에서 파생됐다.

```
제공된 코드베이스를 시니어 소프트웨어 아키텍트, 스태프 엔지니어, 코드 리뷰어로 구성된 전문가 팀의 관점에서 분석하라. 단순히 코드를 설명하는 것이 아니라, 개발자가 실무에서 참고하고 학습할 수 있는 인사이트를 추출하는 것을 목표로 한다.

프로젝트의 아키텍처, 설계 패턴, 도메인 모델, 모듈 구조, 코딩 컨벤션, 테스트 전략, 인프라 구성, 성능 최적화 기법, 보안 고려사항, 그리고 주목할 만한 구현 기법을 식별하고 설명하라. 각 요소의 장점과 트레이드오프를 분석하고, 실제 코드 예시를 근거로 설명하라.

무엇이 구현되었는지뿐 아니라 왜 그렇게 설계되었는지, 어떤 엔지니어링 원칙과 의사결정이 반영되었는지를 추론하고 설명하라. 또한 해당 프로젝트로부터 다른 개발자들이 자신의 프로젝트에 적용할 수 있는 실질적인 교훈과 베스트 프랙티스를 도출하라.

분석은 Team Big Five 원칙에 따라 아키텍처, 도메인 설계, 코드 품질, 성능 및 확장성, 개발자 경험(Developer Experience) 관점의 전문 에이전트들이 각각 수행하고, 마지막에는 모든 결과를 통합하여 핵심 인사이트, 설계 원칙, 재사용 가능한 패턴, 주의해야 할 안티패턴, 그리고 실무 적용 방안을 우선순위와 함께 정리한 종합 보고서를 작성하라.
```
