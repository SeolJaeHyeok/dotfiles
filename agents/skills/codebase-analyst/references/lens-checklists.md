# 렌즈별 분석 체크리스트

> 각 분석 에이전트는 **자기 렌즈 섹션만** 읽는다. 체크리스트는 "무엇을 볼지"의 출발점일 뿐, 코드에서 드러나는 실제 신호를 우선한다. 체크리스트에 없어도 주목할 만한 것은 보고하고, 체크리스트에 있어도 해당 코드베이스에 없으면 건너뛴다 (오버피팅 금지).

**모든 렌즈 공통 원칙:**
- **근거 우선**: 모든 발견은 `path/to/file.ext:line` 인용으로 뒷받침한다. 근거 없는 일반론 금지.
- **Why 추론**: "무엇이 구현됐나"에서 멈추지 말고 "왜 이렇게 설계됐나 — 어떤 제약·원칙·트레이드오프가 반영됐나"를 추론한다.
- **양면 평가**: 장점과 트레이드오프를 함께 본다. 칭찬만 하거나 비판만 하지 않는다.
- **학습 추출**: "다른 개발자가 자기 프로젝트에 가져갈 수 있는 것"을 항상 염두에 둔다.

---

## architecture (codebase-architect)

**핵심 질문:** 이 시스템은 어떻게 구조화되어 있고, 그 구조가 어떤 결정의 산물인가?

- **아키텍처 스타일**: layered / hexagonal(ports&adapters) / clean / modular monolith / microservices / event-driven / serverless 중 무엇에 가까운가? 순수한가 혼합인가?
- **모듈 경계**: 최상위 모듈/패키지 분할 기준 (기능별 vs 레이어별 vs 도메인별). 경계가 명확한가, 누수(leaky)인가?
- **의존성 방향**: 의존성이 한 방향으로 흐르는가? 순환 의존(circular dependency)이 있는가? 안정적 의존성 원칙(SDP)을 따르는가?
- **통신 패턴**: 동기/비동기, REST/gRPC/GraphQL/메시지큐/이벤트. 모듈 간 결합 방식.
- **경계면(boundary)**: API 계약, DTO/스키마, anti-corruption layer, 외부 시스템 통합 지점.
- **확장 지점**: 플러그인, DI 컨테이너, 전략 패턴, 설정 기반 분기 — 어디가 변경에 열려 있나.
- **횡단 관심사(cross-cutting)**: 인증/인가 경계, 로깅, 트랜잭션, 에러 전파가 어디서 어떻게 처리되나.
- **보안 경계(아키텍처 관점)**: trust boundary, 인증 게이트웨이 위치, 권한 검사 계층.

## domain (codebase-domain-designer)

**핵심 질문:** 비즈니스 도메인이 코드에 얼마나 충실하고 표현력 있게 모델링됐는가?

- **도메인 모델**: 핵심 엔티티/값 객체(value object)/애그리거트(aggregate). 빈약한 모델(anemic)인가 풍부한 모델(rich)인가?
- **유비쿼터스 언어**: 코드의 네이밍이 도메인 용어와 일치하는가? 기술 용어가 도메인을 가리고 있지 않은가?
- **바운디드 컨텍스트**: 서로 다른 의미의 같은 개념이 분리돼 있는가? 컨텍스트 경계가 코드에 드러나는가?
- **도메인 로직 위치**: 비즈니스 규칙이 도메인 계층에 모여 있는가, 컨트롤러/서비스/UI에 흩어져 있는가?
- **추상화 수준**: 추상화가 도메인을 명료하게 하는가, 불필요한 간접 계층(indirection)을 만드는가?
- **불변식(invariant)**: 도메인 규칙·제약이 타입/생성자/팩토리로 강제되는가, 런타임 검증에 의존하는가?
- **상태/생명주기**: 엔티티 상태 전이가 명시적인가 (상태 머신 vs 산발적 플래그).
- **DDD 패턴**: repository, factory, domain event, specification 등의 적용 여부와 적절성.

## quality (codebase-quality-reviewer)

**핵심 질문:** 이 코드를 다른 개발자가 읽고, 고치고, 신뢰할 수 있는가?

- **가독성**: 명명, 함수 길이, 중첩 깊이, 매직 넘버, 주석의 질(왜 vs 무엇).
- **예측가능성**: 같은 이름은 같은 동작을 하는가? 숨은 사이드 이펙트가 있는가? 일관된 반환/에러 규약.
- **응집도/결합도**: 한 모듈이 하나의 책임에 집중하는가? 모듈 간 결합이 느슨한가?
- **코딩 컨벤션**: 린터/포매터(eslint/prettier/biome/ruff 등) 설정 존재와 준수. 스타일 일관성.
- **테스트 전략**: 단위/통합/e2e 비율, 테스트 위치/네이밍, 픽스처·목 사용, 커버리지 접근. 테스트가 행위를 검증하나 구현을 검증하나?
- **에러 핸들링**: 예외 vs 결과 타입, 에러 전파, 경계에서의 검증, 삼켜진(swallowed) 예외.
- **안티패턴·코드 스멜**: god object, 중복, 죽은 코드, 과한 추상화, 누수 추상화, 순환 참조.
- **기술 부채 신호**: TODO/FIXME/HACK 밀도, 우회(workaround)·임시 코드, 버전 고정 흔적.
- **보안(코드 관점)**: 입력 검증, 인젝션 방어, 비밀값 하드코딩, 의존성 취약점 신호.

## performance (codebase-performance-analyst)

**핵심 질문:** 부하가 늘고 데이터가 커져도 이 시스템은 버티는가? 어디가 먼저 무너지는가?

- **병목 후보**: N+1 쿼리, 동기 블로킹 I/O, 직렬 처리해도 될 것의 병렬 누락, 핫 패스의 불필요한 연산.
- **데이터 접근**: DB 쿼리 패턴, 인덱싱, 페이지네이션, 배치 vs 개별, ORM 사용 방식(lazy/eager).
- **캐싱**: 캐시 계층(메모리/Redis/CDN/HTTP), 무효화 전략, 캐시 키 설계, 캐시 스탬피드 방어.
- **동시성·병렬성**: async/await, 스레드/워커 풀, 락·경쟁 조건, 멱등성(idempotency).
- **확장 전략**: 무상태성(stateless) 여부, 세션/상태 저장 위치, 수평 확장 가능성, 큐 기반 비동기 분리.
- **리소스 관리**: 커넥션 풀, 메모리 누수 위험, 스트리밍 vs 전량 로딩, 백프레셔.
- **인프라 구성**: 컨테이너화(Dockerfile), 오케스트레이션, CI/CD 파이프라인, IaC(Terraform/CDK), 배포 전략(blue-green/canary).
- **관측가능성(observability)**: 메트릭/트레이싱/로깅이 성능 진단에 충분한가.

## dx (codebase-dx-analyst)

**핵심 질문:** 새 개발자가 이 프로젝트에 합류해 첫 기여까지 얼마나 매끄러운가?

- **온보딩**: README의 완결성, setup 단계 수, 한 줄 부팅(`make dev`, `docker compose up`) 가능성, 사전 요구사항 명시.
- **로컬 개발 경험**: 핫 리로드, 시드 데이터, 목 서버, 환경변수 관리(.env.example), 로컬-프로덕션 일치.
- **빌드·툴링**: 빌드 속도, 모노레포 도구(turbo/nx/pnpm), 스크립트 표준화(package.json/Makefile/Taskfile), 의존성 관리.
- **문서화**: 코드 주석 밀도/질, ADR, API 문서(OpenAPI/typedoc), 아키텍처 다이어그램, 인라인 예제.
- **에러·디버깅**: 에러 메시지의 실행가능성(actionable), 스택트레이스 품질, 디버깅 도구·로그 레벨, 실패 시 안내.
- **탐색성(navigability)**: 디렉토리 구조의 직관성, 파일 찾기 쉬움, 일관된 위치 규칙, 진입점 명확성.
- **자동화·가드레일**: pre-commit 훅, CI 검사, 타입 안전성, 코드 생성, 템플릿/스캐폴딩.
- **주목할 구현 기법**: 영리한 idiom, 재사용 가능한 유틸리티, 우아한 추상화 — "이건 배워갈 만하다" 싶은 것.
