# Output Formats

어셈블러가 초안 구조를 결정할 때 참고하는 형식별 가이드. 사용자 브리핑의 "출력 형식"에 따라 해당 섹션만 로드한다.

## 형식 선택 매트릭스

| 사용자 표현 | 매핑 형식 |
|-----------|----------|
| "트렌드 보고서", "동향", "~ 흐름" | 트렌드 보고서 |
| "트러블슈팅", "사후 분석", "포스트모템", "사고 보고서" | 트러블슈팅 보고서 |
| "기술 비교", "~ vs ~", "어느 것이 나을까" | 비교/평가 |
| "시장 분석", "산업 보고서", "투자 동향" | 시장/산업 보고서 |
| "설명", "~란 무엇인가", "비전공자에게" | 개념 설명/교육 |
| "회고", "지난 ~ 정리", "배운 점" | 회고 |
| "백서", "심층 보고서" | 백서 |
| "아티클", "칼럼", "에세이", "포스트" | 아티클 |
| 분류 모호 | 일반 장문 글 |

---

## 1. 트렌드 보고서

**목적**: 특정 영역의 변화를 시간 축으로 정리하고, 방향성을 제시한다.

**구조**:
```
1. TL;DR (3-5줄)
2. 배경 (이 주제가 왜 지금 중요한가)
3. 과거: 어디서 출발했는가 (시간순)
4. 현재: 지금 무슨 일이 일어나고 있는가
   - 추세 1
   - 추세 2
   - 추세 3
5. 변곡점 (게임 체인저)
6. 가까운 미래 (12개월) — 단정 톤 금지, "관전 포인트" 형식
7. 시사점 (독자가 무엇을 해야 하는가)
8. 참고 자료
```

**핵심 원칙**:
- 모든 추세에는 시점과 수치가 붙어야 한다
- "주목받고 있다" 같은 모호한 표현 금지
- 미래 예측은 항상 약화 표현 사용 ("~로 보인다")

---

## 2. 트러블슈팅 보고서 (포스트모템)

**목적**: 사고를 재구성하고, 같은 사고를 막을 수 있는 학습을 추출한다.

**구조**:
```
1. Summary (한 단락: 무엇이 / 언제 / 누구에게 / 얼마나)
2. Impact (정량 영향: 다운타임, 실패한 요청 수, 영향받은 사용자)
3. Timeline (분 단위, 절대시각 + Δ)
4. Root Cause (5 Whys)
5. Contributing Factors (직접 원인 외)
6. What Went Well (대응 잘된 점)
7. What Went Wrong (대응 못한 점)
8. Action Items (담당자, 마감, 우선순위)
9. Lessons Learned (조직 차원의 학습)
10. Appendix (지표, 로그, 차트)
```

**핵심 원칙**:
- **Blameless 톤**: 사람 이름 대신 역할 ("on-call SRE"), 실수가 아닌 시스템 결함으로 서술
- 모든 시각은 UTC 또는 명시된 타임존
- Action Item에 담당자와 마감이 없으면 액션 아이템이 아니다

---

## 3. 비교/평가

**목적**: 두 개 이상의 선택지를 객관적 기준으로 평가하고, 상황별 권장안을 제시한다.

**구조**:
```
1. TL;DR (한 줄 결론 + "단, ~ 경우 예외")
2. 비교 대상 소개 (각각 한 단락)
3. 평가 기준 정의 (왜 이 기준인가)
4. 기준별 비교
   - 기준 1: A vs B
   - 기준 2: A vs B
   - ...
5. 종합 점수 또는 매트릭스
6. 상황별 권장 ("X 상황이면 A, Y 상황이면 B")
7. 한계 (이 비교가 다루지 않은 것)
```

**핵심 원칙**:
- 단일 승자 선언 금지 — 항상 상황별 권장
- 모든 벤치마크는 출처와 측정 환경 명시
- 본인의 편향 인정 섹션 포함

---

## 4. 시장/산업 보고서

**목적**: 산업 현황·동인·기회·리스크를 임원·투자자에게 전달.

**구조**:
```
1. Executive Summary (1페이지 이내, 결론 위주)
2. 시장 정의와 범위
3. 시장 규모 (현재, 과거 5년, 예상)
4. 주요 플레이어 (점유율, 포지셔닝)
5. 성장 동인
6. 리스크 / 역풍
7. 세그먼트별 동향
8. 글로벌 비교
9. 기회 (Where to Play)
10. 결론 / 전략적 시사점
11. 부록 (데이터 테이블, 출처)
```

**핵심 원칙**:
- Executive Summary는 본문 없이도 결정 가능해야 한다
- 모든 수치는 출처와 발행일 명시
- 차트/표 위주, 산문은 보조

---

## 5. 개념 설명/교육

**목적**: 비전공자 또는 입문자에게 새 개념을 이해시킨다.

**구조**:
```
1. Hook (왜 이걸 알아야 하는가, 일상적 예시)
2. 익숙한 것에서 출발
3. 새 개념 도입 (한 번에 하나씩)
4. 비유 (반드시 1개 이상)
5. 작동 원리 (단순 → 복잡)
6. 실제 사례
7. 한계 (이 개념이 안 통하는 경우)
8. 더 알고 싶다면 (다음 단계)
```

**핵심 원칙**:
- 전문 용어 첫 등장 시 반드시 설명
- 한 단락에 새 개념 1개 이하
- "이게 왜 중요한가"를 모든 섹션 시작에서 환기

---

## 6. 회고

**목적**: 지난 작업·기간에서 학습을 추출한다.

**구조**:
```
1. 목표 (시작 시점에 무엇을 하려 했는가)
2. 무슨 일이 있었나 (사실 위주, 시간순)
3. 결과 (달성한 것, 못한 것)
4. 잘된 것 (구체적, 재현 가능한 형태)
5. 못한 것 (반성, 비난 아닌 분석)
6. 배운 것 (일반화 가능한 교훈)
7. 다음에 다르게 할 것 (구체적 액션)
```

**핵심 원칙**:
- 자기 변호 톤 금지
- "운이 좋았다", "운이 나빴다"는 분석이 아니다 — 더 파고들어라
- 외부 독자가 읽어도 학습이 되도록

---

## 7. 백서 (White Paper)

**목적**: 기술/제품/방법론에 대한 권위 있는 심층 문서.

**구조**:
```
1. Abstract (한 페이지)
2. 문제 정의
3. 기존 접근법과 한계
4. 제안하는 접근법
5. 작동 원리 (상세)
6. 검증/실험/벤치마크
7. 적용 사례
8. 한계와 향후 과제
9. 결론
10. 참고 문헌
```

**핵심 원칙**:
- 학술 톤, 단정적이되 검증 가능
- 모든 주장은 인용 가능
- 보통 5000자 이상, 풍부한 도식

---

## 8. 아티클 / 칼럼 / 에세이

**목적**: 의견·관점을 설득력 있게 전달.

**구조**:
```
1. Hook (강한 첫 문장 — 사실, 질문, 도발)
2. 문제 제기
3. 통념 (대부분이 믿는 것)
4. 통념을 깨는 사실/관찰
5. 새 관점 (저자의 주장)
6. 근거 (3-5개)
7. 반론 다루기
8. 결론 (호소 또는 제안)
```

**핵심 원칙**:
- 첫 문장이 약하면 아무도 안 읽는다
- 근거 없는 주장 금지
- 반론을 다루지 않으면 설득력 없다

---

## 9. 일반 장문 글 (분류 모호 시 기본값)

**구조**:
```
1. TL;DR
2. 배경/맥락
3. 본론 (3-5개 섹션)
4. 결론 / 시사점
5. 참고 자료
```

---

## 공통 규칙 (모든 형식 적용)

1. **TL;DR은 본문보다 먼저 작성한다.** TL;DR을 못 쓰면 본문이 아직 정리 안 된 것이다.
2. **모든 섹션 끝에는 다음 섹션으로 넘어가는 연결고리가 있어야 한다.** 단, 강제로 만들지 말고 자연스러운 곳에서.
3. **이미지·표·코드 블록은 본문보다 강력하다.** 적극 사용.
4. **부록은 부록이다.** 본문에서 안 읽어도 되는 디테일만 부록으로.
5. **참고 자료는 마지막에.** 본문 인용은 인라인 링크 또는 각주.
